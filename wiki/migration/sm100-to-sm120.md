# SM100/B200 to SM120/RTX Blackwell Migration

## Migration Rule

Treat SM120 as a Blackwell-family target with different product constraints and different documented GEMM instruction families. Do not blindly port an SM100/B200 optimization plan to RTX PRO 6000 Blackwell.

## Checklist

1. Confirm the target architecture is `sm120`, `sm_120`, `compute_120`, RTX PRO 6000 Blackwell, or GeForce RTX 50.
2. Re-check shared-memory usage against SM120's 100 KB per-SM and 99 KB (101376 B) per-block limits; SM120 also allows only 24 resident CTAs per SM.
3. Recompute occupancy and cluster occupancy for the target GPU.
4. For low-precision GEMM, prefer CUTLASS SM120 paths and PTX `mma.sync` / `mma.sp::ordered_metadata` families.
5. For sparse GEMM, preserve ordered metadata and the sparse tensor-core contract.
6. Do not propose SM100 `tcgen05.mma`, TMEM, or 2-SM cooperative MMA unless the source code already uses a verified SM120 implementation of that feature.
7. Re-profile memory-bound kernels locally because RTX PRO 6000 GDDR7 bandwidth is not B200 HBM bandwidth.

## Failure Evidence Already In The Corpus

- Shared memory: FlashInfer `pr-flashinfer-2670` records a real SM120 tinygemm2 failure caused by a stage count that needed more dynamic shared memory than the SM120 block limit allowed.
- Architecture suffixes: vLLM [vllm#37725](https://github.com/vllm-project/vllm/pull/37725) records a build-path failure where `a/f` CUDA arch suffixes were stripped for SM12x, breaking NVFP4 behavior.
- Backend routing: vLLM `pr-vllm-38423` records SM12x NVFP4 failures caused by tile constraints and backend capability gates.

These examples are useful because they are not generic CUDA failures. Each one came from applying an older or broader Blackwell assumption to an SM120-family target.

## Common Bad Port

The failure mode is:

- Read B200 NVFP4 or SM100 GEMM material.
- Generate `tcgen05.mma` or TMEM code.
- Compile for `sm_120`.
- Hit assembler failures or get a design that does not match the documented SM120 CUTLASS path.

The correct first response is not to keep patching operands. The correct response is to switch to the SM120 source set and choose the matching instruction family.

## Planning Guidance

For KAI planner output on SM120, include:

- target architecture and product family;
- the top profiling bottleneck;
- the SM120-specific source page used;
- whether the candidate needs dense `mma.sync`, sparse `mma.sp::ordered_metadata`, or ordinary CUDA/vectorized memory optimization;
- one implementation recommendation that matches that source.
